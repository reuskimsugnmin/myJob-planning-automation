# PRD Author (PRD 작성)

워크플로우 5단계. 티켓 + 도메인/기술 리서치를 종합해 PRD 초안을 만든다.

## 선행 (모두 읽고 시작)
- `00-project-brief.md`, `research/domain-study.md`, `research/tech-research.md`.
- 기술/정책 사실은 **`research/*.md` + 지식베이스(`.planning/knowledge-base/` 의 tech-registry·policy-registry)를 우선 조회**해 사용한다. **원문 문서를 재페치하지 않는다**(출처는 KB 항목 `id`/문서 인용).
- 없는 입력이 있으면 사용자에게 알리고, 진행 여부를 확인.

## 절차

1. `${CLAUDE_PLUGIN_ROOT}/templates/PRD.template.md` 를 읽어 `PRD.md` 를 채운다.

2. **자동 작성 가능 항목**: 문제 정의, 목표/비목표, 성공 지표(초안), 기능/비기능 요구사항(티켓 요건 + 리서치 근거로 도출, 각 항목에 출처/근거), 의존성·제약(tech-research 연계).

3. **⛳DECISION 항목 (사람 결정 — 자동으로 단정하지 말 것)**:
   - 타겟 사용자, 제품 핵심 밸류, 차별성, 주요 서비스 정책, UX 배치.
   - 각 항목에 대해 **2~3개 옵션 + 트레이드오프 + 추천안**을 제시하고 `⛳DECISION` 으로 표시.
   - 문서 하단 **「⛳DECISION 모아보기」** 에 체크리스트로 수집.

4. **추적성**: 각 요구사항(FR-n)에 근거 출처를 단다. 도메인 스터디의 리스크/빈틈이 요구사항에 반영됐는지 확인.

5. **보고**: 작성된 요구사항 수, 미결 ⛳DECISION 목록을 사용자에게 보고하고, 결정을 받으면 PRD에 반영(`decision-brief`/회의 후 갱신은 Phase 2 스킬). 이어서 `sdd-author` 제안.

## 원칙
- 전략적 결정을 사람 대신 내리지 않는다 — 옵션과 추천까지가 역할.
- 근거 없는 요구사항을 만들지 않는다.
