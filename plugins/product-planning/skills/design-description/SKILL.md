# Design Description (디스크립션 작성·동기화)

워크플로우 12단계. 완성된 디자인을 보고 **뱃지별 기획 디스크립션**을 작성하고, 그 내용을 **실제 디자인에 동기화**한다.
**Description만 수정하고 디자인에 미반영하는 것은 금지** — 두 소스의 불일치는 개발·QA·운영에 잘못된 정보를 준다.

> Figma 노드 조작·폰트 로딩·심볼 INSTANCE 처리·스크린샷 검증 등 "쓰기" 원시는 **`figma-design` 스킬**(특히 §E 폰트·§G 심볼)을 따른다. `use_figma` 전 `/figma-use` 필수.
> 모드: `--scan`(변경 계획만 분석·보고) → 검토 후 `--apply`(적용). 플래그 없으면 전체.
> 상세 레벨: **`--dev-detailed`(기본)** = 개발 착수용 — §4-D 추가 섹션(`[상태]`·`[데이터]`·`[인터랙션]`·`[연동]`·`[엣지/예외]`·`[수용 기준]`)까지 채운다. **`--standard`** = 간략(의도 중심, §4 기본 섹션만, opt-in).

## 선행 — 디스크립션의 "재료"는 PRD다 (화면만 보고 쓰지 말 것)
디스크립션이 얕아지는 1차 원인은 **화면만 보고 일반적 문장을 쓰는 것**이다. 작성 전 반드시:
- **`PRD.md` + `engagements/<slug>/design/policy-table.md`**(있으면 `SDD.md`)를 **로드**한다. 없으면 멈추고 사용자에게 확인(근거 없는 디스크립션 금지).
- 각 요소의 대괄호 필드(`[Validation]`·`[데이터]`·`[상태]`·`[인터랙션]`·`[수용 기준]` 등)는 **그 요소의 FR·유저스토리·수용기준·policy-table 행에서 값을 옮겨** 채우고 `(FR-n)/(US-n)/(P-XX)` 로 출처 인용한다.
- PRD/policy-table에 그 값이 **없으면 지어내지 말고 `[미확정 D-n]`/`⛳DECISION`** 으로 표기(공백을 드러내 사용자/SDD에 위임). 그 `D-n`은 **`policy-table.md` 디자인 의사결정 체크리스트(`decision-checklist` 스키마)에 등록**하고, **서비스정책·기획요건에 영향을 주면 `PRD/SDD C1 D-n`에 등록·본문 갱신(`prd-sdd-editing` 준수) + policy-table엔 `→ PRD D-n` 링크**(고아 마커 금지·`decision-checklist` 영향 기준 분기). "화면을 보니 대충 이럴 것"이라는 추측 서술 금지.

## 0. 핵심 원칙
**커버리지 — 모든 화면.** 대상 페이지의 **모든 SECTION 화면**에 Descriptions 프레임·뱃지가 있어야 완료다. 일부 화면만 작성하고 끝내면 **미완료**이며, 미처리 화면 목록을 사용자에게 보고한다(특정 화면을 의도적으로 제외하려면 사용자 확인). `.md` 파일만 쓰고 캔버스에 뱃지/annotation을 안 만든 화면은 미처리로 본다.

**★ 품질 기준은 모드·생성량 무관하게 동일(드리프트 금지).** 디스크립션 품질 게이트(§4 형식 다줄·§4-D dev 필드·**컴포넌트명 금지**·§5 검증 A/B/B-2/B-3/C)는 **운영(모드 A)·구축(모드 B)·신규·대량 생성 전부 동일 적용**한다. **대량/빠른 빌드일수록 드리프트 위험이 가장 크다**(화면을 올리는 데 급해 역할 한 줄·컴포넌트명·inline로 흐름 — 실패 사례: 적금 테스트는 양식 준수·dev-ready인데 eSIM은 다회차 대량 생성하며 `ui/detail`·`btn54` 누출 + 얕은 주석으로 저하). → **한 번에 N개를 써도 각 주석이 §5 게이트를 통과해야 하며, 배치마다 §5(B-2 형식·B-3 컴포넌트명·B-4 얕음·C dev-readiness)를 스크립트로 돌려** 자동 적발한다. **★ 대량 모드 필수 단계**: 각 배치 시작 시 **사용자 픽스 화면(고품질 예시, 예 적금 테스트)을 먼저 로드해 필드 깊이를 맞춘 뒤** 작성한다(자의 압축 금지). 그 수준을 모든 화면에 맞춘다.

디자인 **정수 뱃지 N** = Description **annotation-frame N**. annotation N의 제목·본문은 **뱃지 N이 화면에서 가리키는 바로 그 UI 요소**를 설명한다. 개수만 맞추는 게 아니라 **무엇을 가리키는지**가 맞아야 한다(개수 OK인데 의미 어긋남이 가장 잦은 결함).

Description 프레임 구조(운영 양식): `Description > [헤더 내비 프리앰블] + annotation-frame × N`. 각 `annotation-frame` 은 텍스트 3개 — **노드명 고정**: `"1"`(뱃지 번호) · `"Section Title.."`(제목) · `"Lorem ipsum..."`(본문). 새 annotation-frame 을 만들 때도 이 노드명·구조를 그대로 따른다.

**헤더 내비 = 배지 1(모든 화면 최상단 상시 · 정식 annotation, 별도 텍스트 프리앰블 금지).** `header/main`의 **백버튼(⬅)·X버튼(✕)** 도 다른 요소처럼 **번호 배지로 편입**한다 — **배지 1**: 화면 SECTION의 백/X 버튼 위치(좌상단)에 `label-group` 배지 1 + Description 최상단에 정본 `annotation-frame`(clone) 배지 1(제목=`뒤로 가기`/`닫기`, 본문=역할문 + `[Action]` 경로 `- ⬅ 뒤로 → {이전화면}`). **기존 콘텐츠 배지·annotation은 +1 재번호**(reading order 상단 우선). 헤더 없는 종료 화면도 배지 1 = `헤더 내비`(본문 `종료 화면·헤더 미노출`). **카운트 불변식(annotation N == 정수 배지 N)은 그대로**(헤더 내비가 배지 1로 정식 편입되므로 예외 아님). ★ raw 텍스트 블록으로 넣지 말 것 — 정본 annotation-frame clone.

### 0-A. 정본 구조 불변식 (재발 방지 — 반드시 준수)
> 과거 사고: 디스크립션을 정본 템플릿 clone 없이 **임의의 새 패널로 발명**했고, 그 전에 "lo-fi 잔재" 정리 중 디스크립션 구조가 붙은 SECTION을 **삭제**해 과거 픽스를 날릴 뻔했다. 아래를 반드시 지킨다.
- **정본 템플릿 clone 필수 · 레이아웃 발명 금지.** Description/annotation-frame/label-group 은 새로 디자인하지 말고 **기존 정본 노드를 clone**해 텍스트(`"1"`/`"Section Title.."`/`"Lorem ipsum.."`)만 교체한다. 임의의 새 패널·뱃지 모양 생성 금지.
- **보호 레이어 · 삭제 금지.** `Description`·`annotation-frame`·`label-group`·`text-area`·`SB_Templates` 행은 cleanup/정리 단계에서 **삭제하지 않는다.** "낡은 lo-fi"로 보여도 주석 레이어·과거 픽스가 함께 묶여 있을 수 있다. 삭제가 필요하면 대상이 디스크립션 구조/과거 픽스가 아님을 확인하고 애매하면 **사용자 확인**(`prd-sdd-editing` 의 ID안정성·유실방지 불변식을 디자인에도 적용).
- **작업 전 재로드.** 디스크립션 작업 시작 시 이 스킬 + 정본 구조 메모리를 먼저 로드해 임의 구조 생성을 차단한다. `.md` 백업이 내용 진실 소스이므로 캔버스 유실 시 .md로 복구한다.
- **3-set 행 배치(운영).** 한 화면 행 = `SB_Templates`(헤더 밴드) **위에** 디자인 SECTION(폭 1375·`#000000 10%`, 디자인 프레임 + 뱃지 **섹션 최상위 z**·디자인과 분리) + **우측** `Description`. 화면 추가는 이 행을 clone해 헤더·프레임·뱃지·annotation 내용만 교체.

## 1. 뱃지 매칭 (수집 · 정수/서브 · 요소 매핑)
- **수집 — 두 구조 모두**: `label-group`(래핑 프레임)과 **단독 `text-area`** 를 둘 다 센다(한쪽만 세면 누락·중복). node id로 dedup, 노출(visible) 뱃지만 대상.
- **정수 vs 서브**: 정수 뱃지(1,2,3…)=각 독립 `annotation-frame` · 서브 뱃지(2a/3-1 등)=독립 프레임 금지, 부모 본문에 `(2a)` fold(디자인의 서브 뱃지는 그대로).
- **요소 매핑**: bbox **가장자리(edge) 거리** 최근접 노출 요소(중심 거리 아님). 후보에 **아이콘 전용 버튼·인터랙션** 포함(빼면 옆 텍스트 오매핑·인접 뱃지 밀림). edge 결과는 `get_screenshot`으로 교차 확인.
- **상세 절차·실패사례는 `references/badge-mechanics.md`를 읽어 따른다.**

## 4. annotation 본문 형식 (정본 — 일관성 필수)
**제목(Section Title) = 가리키는 요소명.** **순수 요소명만 쓴다 — `(CTA)`·`(칩)`·`(입력)`·`(스피너)` 같은 컴포넌트 유형 괄호 수식 금지**(예: `다음 (CTA)`✗ → `다음`✓, `월 납입 금액 (입력)`✗ → `월 납입 금액`✓). 본문 규칙:
- **★ Figma 노드/DS 컴포넌트 이름 금지(가장 잦은 오염).** 아이콘/프레임 이름(`ico/.../call`·`img_..._thumb`·`Frame 378`·`Group 12`·`Property 1=…`)뿐 아니라 **DS 합성 컴포넌트 이름도 금지** — `ui/detail`·`btn54`·`use_form`·`EL_input`·`EL_tab`·`total_set`·`notification`·`Glassmorphism` 등을 본문에 쓰지 마라. **`[컴포넌트] - ui/detail` 같은 줄 자체 금지**(어떤 컴포넌트로 렌더되는지는 **디자인시스템/SDD 레이어**지 디스크립션 레이어가 아니다 — "개발에 도움될 것 같다"는 착각으로 넣지 말 것). **사용자가 보는 기능/대상·동작·규칙**으로 쓴다: `표준 스펙(ui/detail)`✗ → `표준 스펙 표(적용국가·데이터·5G·통신사·유효기간)`✓ · `[컴포넌트] - btn54`✗ → 역할 문장 `총액 결제 버튼`✓. 노드/컴포넌트 id가 필요하면 본문이 아니라 로그에.
- **(a) 역할 문장** — 첫 줄에 요소 역할 1문장, **라벨 없이**. `[개요]` 머리 금지(제목과 중복).
- **(b) 세부 항목** — 해당하는 것만, **대괄호 섹션 라벨 `[항목]`** 로 구분. **`[항목]`은 한 줄 단독으로 쓰고 다음 줄부터 `- 값` 불릿.** 라벨과 값을 한 줄에 붙이는 인라인 금지 — `Validation: 값`✗ 은 물론 **`[Validation] 값` 처럼 대괄호 라벨 뒤에 값을 같은 줄에 붙이는 것도 금지✗**. 올바른 형식:
  ```
  [Validation]
  - 최소 1만원 ~ 최대 300만원
  ```
  표준 라벨·순서: `[노출 조건]` `[Default 상태]` `[컴포넌트 상태]` `[플랫폼 분기]` `[Action]` `[Validation]` `[에러 케이스]` `[미노출 항목]` `[미확정]`. 조건은 `[필드]=[값]`, 정책 참조는 `(P-XX A안)`·`(US-XXX)`. 도메인 값은 `00-project-brief.md`(플랫폼/필드/에러 표준)에서. **작성 시 사용자 픽스 화면 본문을 서식 exemplar로 삼는다**(자의 압축 금지).
- **(b-1) ★ 요소 종류별 필수 필드(작성 시점 양성 체크리스트 — "해당하는 것만"의 구멍을 막는다).** 인터랙티브 요소는 아래 필드를 **작성하면서 채운다**(끝의 §5-C 게이트로 미루지 말 것 — 게이트는 안전망). "이건 해당 안 됨"으로 건너뛰지 말고, 값이 PRD에 없으면 `[미확정 D-n]`.
  | 요소 종류 | 필수 필드 |
  | --- | --- |
  | 입력(텍스트·금액·휴대폰 등) | `[데이터]` + `[Validation]` + `[Default 상태]` + `[에러 케이스]` (+ `[전이]`) |
  | 버튼/CTA | `[Default 상태]` + `[인터랙션]`(제스처→이동화면+params) + `[전이]` + `[엣지/예외]` |
  | 탭·칩 | `[상태]`(선택/비선택) + `[인터랙션]`(전환 결과) |
  | 카드·리스트 행 | `[인터랙션]`(탭→상세+params) + `[데이터]`(표시 필드) |
  | 토글·체크·라디오 | `[Default 상태]`(초기값) + `[인터랙션]` |
  | 셀렉트 | `[Default 상태]` + `[인터랙션]`(시트 오픈) + `[데이터]`(옵션 출처) |
  | 정적 라벨·아이콘(비인터랙티브) | 면제 — 역할 문장만 |
- **(c) `[Default 상태]` — 인터랙티브 컴포넌트는 필수.** 버튼·CTA·토글·체크박스·탭·입력이면 진입 시 최초 상태와 전이 조건을 명시: 상시 Enabled(`- Default: Enabled (상시 활성)`) 또는 조건부(`- Default: Disabled → [약관 동의]=true & [필수 입력]=완료 시 Enabled`). ON/OFF·선택은 최초값도. 디자인의 시각 상태(흐림/비활성색)와 일치.
- **(d) 서브 뱃지** — `[세부]` 섹션에 `(Na) 요소명: 설명` 한 줄씩.
- **(e) 오버레이 배지 = parent + 액션 하위배지** · **(f) 안내 문구 = 인포박스 variant(red/blue/gray)** — **상세는 `references/desc-format.md`를 읽어 따른다.**
- 플로우차트(CONNECTOR 1개 이상)면 `[플로우]` 항목 추가. 숨김 노드(`visible=false`)는 `[미노출 항목]`.
- 짧은 단일 요소는 (a) 역할 문장만으로 충분(섹션 라벨 없이 평문 1~2문장 허용).

`${CLAUDE_PLUGIN_ROOT}/templates/design/design-description.template.md` 의 슬롯 포맷을 따른다.

### 4-D. 개발자 상세 모드 (`--dev-detailed` = 기본 작성 요건)
개발자가 화면만 보고 구현할 수 있게 **작성 시점에** §4-b1 종류별 필수 필드를 채운다(부록 아닌 **기본 작성 요건**). 필드: `[상태]`·`[데이터]`·`[인터랙션]`·`[연동]`·`[엣지/예외]`·`[수용 기준]`. **지어내기 금지** — 미정은 `[미확정 D-n]`(→ `policy-table.md` 디자인 의사결정 체크리스트, 데이터/API 계약은 SDD C1). **데이터/API 계약은 SDD 링크만**. **각 필드 정의·예시는 `references/desc-format.md`를 읽어 따른다.**

## 5. 작성 검증 (2단계 — 둘 다 필수)
- **(A) 개수**: `annotation-frame 수 == 정수 뱃지 수`(헤더 내비 배지 1 포함 — 정식 배지). 각 서브 Na는 부모 N 본문에 `(Na)` 줄 존재. **모든 화면 Description 최상단 annotation = 배지 1 헤더 내비**인지 확인.
- **(B) 의미(누락 잦음)**: 각 뱃지 좌표 **최근접 요소 == annotation 제목**인지 `get_screenshot` 교차검증. 다르면 정정. 개수만 맞고 헤더↔카드가 뒤바뀐 통과를 막는다.
- **(B-2) 형식(★ inline 드리프트 방지 — 스크립트).** 본문은 `역할문장.\n[항목]\n- 값` **다줄** 정본 — `[상태] - … [인터랙션] - …` 한 줄(inline) 드리프트 적발(줄바꿈 수 ≥ 대괄호 수). 미만이면 줄바꿈 재배치.
- **(B-3) 컴포넌트명 누출(★ 스크립트).** 본문에 Figma/DS 컴포넌트 이름(`ui/detail`·`btn54`·`use_form`·`EL_*` 등)이 섞이면 미통과(§4 위반) → 사용자-기능 표현으로 교체.
- **(B-4) 얕음 객관 탐지(★ "역할 한 줄" 적발 — 스크립트).** 인터랙티브 요소(버튼·입력·탭·칩·카드 등) annotation은 본문에 **대괄호 섹션 `[항목]` 2개 이상**(또는 §4-b1 필수 라벨 존재)이어야 한다. 미만이면 "역할 한 줄" 얕음 → 보강(정적 라벨·아이콘은 §4-b1 면제 제외).
- **B-2·B-3·B-4 점검 스크립트: `scripts/desc-verify.js`**(annotation `title`·`body`에 바인딩해 실행).
- **(C) dev-readiness(★ 마감 게이트 = 안전망 — "개발자가 이것만 보고 구현 가능한가").** **1차 적용은 작성 시점(§4-b1 종류별 필수 필드)이고, 이 게이트는 누락을 잡는 안전망이다**(B-4가 객관 1차 적발). `--dev-detailed`(기본)에서 **액션·입력·동적 요소** annotation은 §4-D 필수 필드를 채워야 한다: `[상태]`(다상태 시)·`[인터랙션]`(제스처→결과+이동화면+params)·`[데이터]`(필드·타입·포맷·범위)·`[전이]`·`[엣지/예외]`·`[수용 기준](US-n)`. **역할 한 줄만 있고 상태·인터랙션·데이터가 비면 미완**(실패: 카운트만 맞고 dev가 못 만드는 디스크립션). 미정 값은 지어내지 말고 `[미확정 D-n]`/`⛳DECISION`으로 표기해 **사용자/SDD에 위임**(이게 "사용자가 해결할 것"을 드러내는 장치다). 정적 라벨·아이콘만인 요소는 면제.
- 자동 판정 가능한 것(개수·서브 접힘·`[개요]` 잔존·인라인 라벨)은 스크립트로, 의미(제목=대상)는 `semantic` 표 + 스크린샷으로 사람이 대조.

## 6. 디자인 동기화 (Description → Figma)
Description write 작업은 **디자인 동기화까지 완료해야 작업 완료**다.

| Description 내용 | 디자인 액션 |
| --- | --- |
| "[요소]: X 조건 시 미노출" | 노드 `visible=false` |
| "[요소]: Y 조건 시 노출" | 노드 `visible=true` |
| "표기/노출 필수" 명시 + 노드 특정 가능, 현재 미반영 | `visible=true` 적용 (**SKIP 금지**) |
| 컴포넌트 Default 상태(예 Default=Disabled) | 명시 상태 variant로 `setProperties` swap. variant 없으면 visible/스타일, 구조 불일치 시 SKIP+수동 |
| 텍스트 값 명시 | TEXT 노드 `characters` 업데이트 |
| 조건부 노출(`[필드]=[값]`) | conditional 표시 후 기획 확정 예시 상태로 노출 |
| 오버레이(셀렉트/안내 시트·팝업) 트리거 | 트리거 화면 옆 상태 프레임으로 §M 정본 clone 배치 |
| 안내 문구(부정/긍정/중립) | §M-6 인포박스 variant(red/blue/gray)로 교체 (raw 캡션 금지) |
| 결과 상세 데이터(계좌·금액 등) | §M-7 `ui/detail` 라벨+값 행으로 (bespoke 카드 금지) |

**SKIP 허용**(`SKIP: [이유]` 기록 + 사용자 확인)은 ① 노드 ID 특정 불가 ② 다수 노드 불확실 ③ 플랫폼 분기 불명확 ④ variant 구조 불일치, 4경우뿐. 동기화 미반영 시 심볼(INSTANCE) 의심 → `figma-design` §G(전 인스턴스 스왑/detach) → 스크린샷 검증.

**동기화에 토큰·컴포넌트 매칭도 포함.** 디스크립션이 가리키는 입력/선택/바텀 액션 요소가 bespoke 도형이면 `figma-design` §L의 DS 컴포넌트(`use_form` 타입별·`btn54_main_set`)로 교체하고, 손작업 텍스트/색은 §K로 DS 변수에 바인딩한다(raw hex 잔존 0). 디스크립션 claim과 디자인이 같아도 토큰·컴포넌트가 bespoke면 미완료.

## 7. 완료 게이트 — 3자 매칭 (뱃지↔디스크립션↔디자인) claim↔노드 대조표 (필수 HITL · 단정 금지)
**"동기화 0건 / 이미 일치"는 그 자체로 완료 근거가 아니다.** 반드시 대조표로 증명한다. **대상은 대상 페이지의 모든 행** — 해피패스뿐 아니라 `storyboard-build` §6에서 추가한 **상세-케이스 화면(에러·empty·valid·로딩) 행도 포함**해 전 행을 대조한다(일부 행만 통과는 미완료).
- **절차**: 각 화면 annotation 본문에서 노출/상태/텍스트 claim(`미노출`·`노출`·`Default=Disabled`·`ON/OFF`·텍스트 값)을 전부 추출 → 각 claim의 **노드를 id로 조회**해 `visible`/variant/`characters` 실제값을 읽고 → **claim=실제 대조표** 작성.
- 불일치(✗) 1건이라도 있으면 미완료 → §6대로 수정하거나 SKIP+확인. **변경 0건이어도** 모든 claim=일치 ✓ 대조표를 **증거로 남겨야** 완료(표 없는 "0건" 보고는 미완료).
- 전형적 실패: 디스크립션엔 `visible=false` 인데 실제 노드는 `true` — "0건 일치"로 단정하면 못 잡는다. 대조 후에야 발견·수정.
- 이 대조표는 동기화 단계의 **출력 필수 산출물**. 작업 완료 시 사용자에게 대조표 + 스크린샷으로 보고.
- **★ 마감 = 리플로우 자동 실행(필수 게이트).** 디스크립션을 편집했으면 Description 높이가 바뀌므로, 작업을 끝내기 전 **`figma-design` §A 자동 발견 리플로우 루틴을 항상 실행**한다(SB 카드 height 리사이즈 + 전 행 Y cascade, 겹침 0). 사용자가 따로 요청하지 않아도 자동. 리플로우 매칭 카운트를 보고에 포함.
  - **Description은 반드시 `primaryAxisSizingMode='AUTO'`(콘텐츠 hug)** — FIXED면 주석 텍스트 증가 시 조용히 오버플로해 아래 행 침범(실패 사례 e05: 697 frame에 1204 콘텐츠). 편집 후 AUTO 확인.
  - **완료 조건 = bbox 교차 0을 `absoluteBoundingBox`+자식 콘텐츠 extent로 확인**(`node.height` 금지 — FIXED 오버플로를 못 본다. `storyboard-build` §8 스니펫). 격리 스크린샷은 겹침을 숨기므로 좌표로 검증.
  - **리플로우 직후 `storyboard-build` §9 자동 마감 검수 게이트(7항목)를 이어서 실행**한다(사용자 요청 불필요). 디스크립션 편집은 #3·#4(배지↔디스크립션·양식)와 #5(엣지케이스→디자인 존재)를 건드리므로 검수 리포트로 누락을 드러낸다.
